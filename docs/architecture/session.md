# Session

What the design adds to the [glossary](../../GLOSSARY.md)'s terms in the `session` module, on the server and in the UI. The design shared by every module is in [the architecture](README.md).

- A message sent while the run is busy is written to the harness at once, but not to the transcript: the session keeps it in its `pendingMessages`. The harness reports the moment the agent takes it (`message_read`; Claude Code's `command_lifecycle` line in state `started`, which names the `uuid` ivin gives the message line). The server then appends its `user_message`, with `steer: true` if a turn was running, or as a message that starts a turn if that turn had ended. `session.interrupt` with pending messages stops the agent's process instead of interrupting it, because Claude Code starts its queued messages as the next turn after an interrupt; those messages move to the session's `unreadMessages`, which the UI puts back in the composer and the next message clears. A run that ends for any other reason, and a server restart, do the same. `session.sendNow` interrupts the turn so the agent starts the pending messages as the next one.
- A session stores its working folder and branch. Before its first message it runs in the checkout; the first message may ask for a new worktree or for one of the project's existing worktrees instead. A new worktree is created under `<project>/.worktrees/<branch with / replaced by ->` on the branch `ivin/<first 8 characters of the session id>` (with `-2`, `-3`… when a branch or a registered worktree already has that name), from `origin/<default branch>` after a fetch of `origin` (30 s timeout, skipped when the last one is younger than two minutes, never moving the checkout). Meanwhile the session's status is "preparing worktree"; the run starts only once the worktree exists. An existing worktree must still be one of the project's when the message arrives. Either way a `working_folder` event records the change and its cause (`creation` or `choice`). When git refuses, its output is stored as an `error` event; the message is not sent either way.
- A session stores its title and who set it (`title_source`). A new session is "New session"; the first message sets the title to its first line, cut to 60 characters, unless the agent or the user already set one. `session.rename` takes `by`: the user, the default, always renames; the agent (`ivin session rename`) renames unless the user did, and gets `SessionTitleChosenByUser` otherwise.
- The server reads a session's first message in the background, without holding the turn (`FirstMessageReading`). It asks the harness's small model (`completeText` on the `HarnessProvider` port; Claude's runs `claude -p --model haiku` with no tools, settings, hooks, skills, MCP servers or saved session, 30 s at most) for a title of a few words and for the issue or pull request number the message names. The title replaces the first message's only while `title_source` is still `message`, and is stored as `generated`. The number, kept only when the message holds it, becomes a `citation` annotation (`{ kind, number }`, namespace `ivin`) whatever the title: the core knows no forge, so the forge's plugin turns it into a link. A failure leaves the first-line title and no citation, and goes to the log only. A harness without `completeText` gets neither.
- A session stores its run options: model, effort and permission mode. Each provider lists the values it offers, with the name the user reads, and a default for each (`runOptions` on the `HarnessProvider` port, an effect, sent to the UI by `server.getHarness`); each model also lists the effort levels it takes. Claude's provider asks Claude Code for its models (an `initialize` control request to a `claude -p` process it stops at the answer), keeps its first answer, and offers its four aliases when Claude Code does not answer. The server checks none, so a value the harness refuses fails in the agent. A new session takes the last options set in its project, at creation or by a change, keeping each value its harness still offers and the harness's default otherwise. `session.setRunOptions` changes them at any time and, after the session's first message, appends one `run_option` event per changed option, with the old and new value and their names at the time. The change applies from the next message: a turn already running finishes with its process, and the next message after it stops that process and resumes the conversation (`--resume` for Claude) with the new options; no in-process control request is used. The server keeps the options of the last run whose first turn ended without an error. When the first turn of a run started with other options ends with an error, or the run stops before that turn ends, the session carries a relaunch failure: those previous options and the message's text, which the UI puts back in the composer while offering to return to them. The next message or change clears it.
- A session in a worktree that `git worktree list` no longer shows (removed by git, or its folder deleted) is marked as having a deleted working folder, checked when its tab opens and before each message. It keeps its transcript and refuses messages until the user picks the checkout, an existing worktree or a new one (`session.pickWorkingFolder`). The pick ends the agent's process, records a `working_folder` event with the cause `pick`, and the next message resumes the conversation in the new folder.
- The session follows the folder its agent works in. While a run is open, the harness describes each successful tool call (`toolActivity` on the `HarnessProvider` port): the agent switched itself to a folder (Claude's `EnterWorktree` and `ExitWorktree`), ran a shell command, or did something else, with its input. The server knows no tool names: a tool call item also carries the `kind` the harness gives its tool (`toolKind` on the port: command, read, edit, search, skill, agent or other), set when the server derives the item, so old transcripts get it too. After a folder switch, the session moves to that folder if it is the checkout or a worktree git lists. After each shell command it reads `git worktree list`; a worktree that appeared during the run is the agent's, and the session moves there once a later command, or the part of the creating command after `git worktree add`, names its path (absolute, or relative to the working folder), or another tool's input names a file in it. Creating a worktree alone moves nothing. The move is a `working_folder` event with cause `adoption`. The Claude process keeps its folder until its turn ends; the next message stops it and resumes the conversation with `--resume` in the new folder.
- Before the first message, a session in the checkout can switch the checkout to the default branch (`session.switchToDefaultBranch`) or fast-forward its branch from `origin/<branch>` (`session.fastForward`), both after the same reused fetch, and only by fast-forward: a diverged branch fails with git's output, never merged or rebased. A switch with local changes is refused unless the user chose to stash or commit them; a pull just runs, and git's refusal says whether local changes caused it. Neither runs while another session's agent works in the checkout, and both update the branch of every session in it. `worktree.checkoutStatus` tells the UI the branch, the default branch, whether a worktree holds it, and how many commits the branch can fast-forward.
- Archiving a session (`session.archive`) ends its agent's process whatever `tabs.stopAgentOnClose` says, closes its tab and stores when it was archived; restoring it (`session.restore`) clears that, and it comes back without a tab. Deleting a session (`session.delete`) ends its agent's process, then erases the session, its transcript events and its tab in one transaction. `session.list` and `session.watch` leave archived sessions out, and `session.watch` streams a session archived or deleted as removed; `session.listArchived` lists them, most recently archived first. Both run the [worktree cleanup](worktree.md) as a closed tab does.
