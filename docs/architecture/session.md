# Session

What the design adds to the [glossary](../../GLOSSARY.md)'s terms in the `session` module, on the server and in the UI. The design shared by every module is in [the architecture](README.md).

- A message sent while the run is busy is written to the harness at once, but not to the transcript: the session keeps it in its `pendingMessages`. The harness reports the moment the agent takes it (`message_read`; Claude Code's `command_lifecycle` line in state `started`, which names the `uuid` ivin gives the message line). The server then appends its `user_message`, with `steer: true` if a turn was running, or as a message that starts a turn if that turn had ended. `session.interrupt` with pending messages stops the agent's process instead of interrupting it, because Claude Code starts its queued messages as the next turn after an interrupt; those messages move to the session's `unreadMessages`, which the UI puts back in the composer and the next message clears. The UI puts each unread message in the draft once, remembering their ids in an atom that outlives the composer, and reads their images from the URL the transcript serves sent images from, so text the user removed does not come back on a tab switch. A run that ends for any other reason, and a server restart, do the same. `session.sendNow` interrupts the turn so the agent starts the pending messages as the next one.
- Each session has one lock over its run. `session.sendMessage`, `session.interrupt`, `session.sendNow`, answering an approval or a question, `session.archive` and `session.delete` take their turn one at a time; sessions do not wait for each other. `sendMessage` runs to its end even when the client stops waiting. In the UI, each send records its own failure and puts its own draft back in the session's atoms, whether or not its composer is on screen, because concurrent calls of one mutation atom share a result. Under the lock a send reads the session again and is refused (`SessionNotFound`) when it was deleted or archived meanwhile; archive and delete stop the run and write their change under the same lock, so they wait for a send that is still starting. The run's own end never takes the lock, because a stop holds it while closing the run.
- A run ends one way whatever the cause (the agent exits, the harness fails, a database error, Stop, archive, delete): its process is stopped, the run is removed, the approvals and questions still open become unanswered (a `request_unanswered` event each, as at the end of a turn and, for a session left waiting, at startup), pending messages move to `unreadMessages`, and the session becomes "idle", or "failed" with an `error` event in the transcript and the error in the log. Each step is attempted even when the one before it failed.
- 10 seconds after `session.interrupt` (or `session.sendNow`), if the same turn is still open, the server takes the path of an interrupt with pending messages: it stops the agent's process, records an `interruption` and sets the session "idle". The next message resumes the conversation in a new process. An agent that ends its turn in time is left running.
- A session stores its working folder and branch. Before its first message it runs in the checkout; the first message may ask for a new worktree or for one of the project's existing worktrees instead. A new worktree is created under `<project>/.worktrees/<branch with / replaced by ->` on the branch `ivin/<first 8 characters of the session id>` (with `-2`, `-3`… when a branch or a registered worktree already has that name), from `origin/<default branch>` after a fetch of `origin` (30 s timeout, skipped when the last one is younger than two minutes, never moving the checkout). Meanwhile the session's status is "preparing worktree"; the run starts only once the worktree exists. An existing worktree must still be one of the project's when the message arrives. Either way a `working_folder` event records the change and its cause (`creation` or `choice`). When git refuses, its output is stored as an `error` event; the message is not sent either way.
- A session stores its title and who set it (`title_source`). A new session is "New session"; the first message sets the title to its first line, cut to 60 characters, unless the agent or the user already set one. `session.rename` takes `by`: the user, the default, always renames; the agent (`ivin session rename`) renames unless the user did, and gets `SessionTitleChosenByUser` otherwise.
- The server reads a session's first message in the background, without holding the turn (`FirstMessageReading`). It asks the harness's small model (`completeText` on the `HarnessProvider` port; Claude's runs `claude -p --model haiku` with no tools, settings, hooks, skills, MCP servers or saved session, 30 s at most) for a title of a few words and for the issue or pull request number the message names. The title replaces the first message's only while `title_source` is still `message`, and is stored as `generated`. The number, kept only when the message holds it, becomes a `citation` annotation (`{ kind, number }`, namespace `ivin`) whatever the title: the core knows no forge, so the forge's plugin turns it into a link. A failure leaves the first-line title and no citation, and goes to the log only. A harness without `completeText` gets neither.
- A session stores its run options: model, effort and permission mode. Each provider lists the values it offers, with the name the user reads, and a default for each (`runOptions` on the `HarnessProvider` port, an effect, sent to the UI by `server.getHarness`); each model also lists the effort levels it takes. Claude's provider asks Claude Code for its models (an `initialize` control request to a `claude -p` process it stops at the answer), keeps its first non-empty answer; when Claude Code does not answer, it offers its four aliases and asks again at the next question. The server checks none, so a value the harness refuses fails in the agent. A new session takes the last options set in its project, at creation or by a change, keeping each value its harness still offers and the harness's default otherwise. `session.setRunOptions` changes them at any time and, after the session's first message, appends one `run_option` event per changed option, with the old and new value and their names at the time. The change applies from the next message: a turn already running finishes with its process, and the next message after it stops that process and resumes the conversation (`--resume` for Claude) with the new options; no in-process control request is used. The server keeps the options of the last run whose first turn ended without an error. When the first turn of a run started with other options ends with an error, or the run stops before that turn ends, the session carries a relaunch failure: those previous options and the message's text, which the UI puts back in the composer while offering to return to them. The next message or change clears it.
- A session in a worktree that `git worktree list` no longer shows (removed by git, or its folder deleted) is marked as having a deleted working folder, checked when its tab opens and before each message. It keeps its transcript and refuses messages until the user picks the checkout, an existing worktree or a new one (`session.pickWorkingFolder`). The pick ends the agent's process, records a `working_folder` event with the cause `pick`, and the next message resumes the conversation in the new folder.
- The session follows the folder its agent works in. While a run is open, the harness describes each successful tool call (`toolActivity` on the `HarnessProvider` port): the agent switched itself to a folder (Claude's `EnterWorktree` and `ExitWorktree`), ran a shell command, or did something else, with its input. The server knows no tool names: a tool call item also carries the `kind` the harness gives its tool (`toolKind` on the port: command, read, edit, search, skill, agent or other), set when the server derives the item, so old transcripts get it too. After a folder switch, the session moves to that folder if it is the checkout or a worktree git lists. After each shell command it reads `git worktree list`; a worktree that appeared during the run is the agent's, and the session moves there once a later command, or the part of the creating command after `git worktree add`, names its path (absolute, or relative to the working folder), or another tool's input names a file in it. Creating a worktree alone moves nothing. The move is a `working_folder` event with cause `adoption`. The Claude process keeps its folder until its turn ends; the next message stops it and resumes the conversation with `--resume` in the new folder.
- Before the first message, a session in the checkout can switch the checkout to the default branch (`session.switchToDefaultBranch`) or fast-forward its branch from `origin/<branch>` (`session.fastForward`), both after the same reused fetch, and only by fast-forward: a diverged branch fails with git's output, never merged or rebased. A switch with local changes is refused unless the user chose to stash or commit them; a pull just runs, and git's refusal says whether local changes caused it. Neither runs while another session's agent works in the checkout, and both update the branch of every session in it. `worktree.checkoutStatus` tells the UI the branch, the default branch, whether a worktree holds it, and how many commits the branch can fast-forward.
- Archiving a session (`session.archive`) ends its agent's process whatever `tabs.stopAgentOnClose` says, closes its tab and stores when it was archived; restoring it (`session.restore`) clears that, and it comes back without a tab. Deleting a session (`session.delete`) ends its agent's process, then erases the session, its transcript events and its tab in one transaction. `session.list` and `session.watch` leave archived sessions out, and `session.watch` streams a session archived or deleted as removed; `session.listArchived` lists them, most recently archived first. Both run the [worktree cleanup](worktree.md) as a closed tab does.
- An agent whose session has had no turn for `agents.stopWhenIdleMinutes` (10 by default; 0 keeps agents running) is stopped. When a turn ends idle, the run forks a timer; when it fires it takes the session lock and stops the run as `session.stop` does, only if it is still the same run, not busy, and on the same turn. An open approval or question, or a pending message, makes it wait one more limit; a turn the agent starts on its own ends with a new timer. The session stays idle with no transcript event, and the next message starts a new agent that resumes the conversation with the stored provider session id. Stopping ends Claude Code's background shells and monitors; a session in background is not stopped, since its tasks run in the agent.
- A stored session whose pending or unread messages, or run options, no longer match their schema shows with them empty, and the problem is logged. A relaunch failure stored before the agent's error was kept gets `error: null` from the schema's default.
- A task is a subagent or a command the agent starts in the background. The harness reports it as a `task_started` event (the task's id, the tool call that started it, its kind and description) and, once it ends, a `task_ended` event (completed, failed or stopped, with a summary, and a command's output as it ended, cut to its last 64 KB). Both derive one `task` item, kept by its start position and updated in place, like a tool call. A subagent's steps carry the `parentToolCallId` of that call, on the events and the items; the server stores a step only while a task of that call runs, so a subagent the turn waits for adds nothing, and `transcript.getTaskItems` returns a task's steps. Claude Code's `system` lines `task_started` (with `is_backgrounded`) and `task_notification` are decoded as these events; the file a task writes its output to is learned from the result of the call that started it and kept in memory for the run (`task_output_file`, never stored), and `session.taskOutput` reads the end of it through the harness's `readTaskOutput` while the task runs.
- The session's `backgroundTasks` (its running tasks, in start order, stored with the session) follow the task events. When a turn ends idle while a task runs, the status is `in_background`, not `idle`; the turn Claude Code starts on its own when a task ends sends `status: "requesting"`, which sets `working` again; the last task ending with no turn running sets `idle`. A task that starts while a turn runs changes no status. The idle timer waits one more limit while a task runs. Interrupting a session in background has no turn to stop, so it stops the run as archiving does; every way a run ends writes `task_ended` as stopped for each open task (and fails the calls its subagent left running) and empties `backgroundTasks`, as it closes open requests, and so does a start that finds a session left in background. A session in background counts as busy for checking out a branch in its folder.
