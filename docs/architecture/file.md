# File

What the design adds to the [glossary](../../GLOSSARY.md)'s terms in the `file` module, on the server and in the UI. The design shared by every module is in [the architecture](README.md).

- A link in an agent's answer that names a file opens it as a sub-view, the way the Files tree does, and so does inline code whose whole text names a file (`inlineCodeTarget`: a relative path only when `file.listFiles` lists it, an absolute path or a `file://` URL when it has a `/` or an extension with a letter; [ADR-0016](../adr/0016-inline-code-opens-a-relative-path-only-when-the-working-folder-lists-it.md)) and the file of a Read, Edit, Write or MultiEdit row, through the plugin API's `FilePath`: a relative path (from the working folder), an absolute path or a `file://` URL, with an optional line or range (`x.ts:42`, `x.ts:42:7`, `x.ts:42-50`, `x.ts#L42-L50`). The file view opens scrolled to those lines, selected; the request lives only in the UI, so the stored sub-view and a reopened file keep their own scroll. A missing file gets the file view's own message. Inline code that is a domain with a common top-level domain, and that names no listed file, links to `https://` and its text. A path outside the working folder opens read-only ([ADR-0015](../adr/0015-the-file-view-reads-a-file-outside-the-working-folder-read-only-when-the-user-opens-it.md)): its sub-view stores the absolute path, `file.readOutsideFile` reads it each time it is shown, and it is never followed on disk or written.
- `file.readFile` reads a file of a session's working folder with the same path check as `file.listFolder`. A raster image, told by its extension (png, jpg, gif, webp, avif, bmp, ico), comes back as its bytes in base64 with its MIME type, up to 10 MiB (`IMAGE_SIZE_LIMIT`); the window shows it from a `data:` URL. Any other file above 2 MiB (`FILE_SIZE_LIMIT`) answers `too_large`, with the limit it went over, without being read, and `binary` when a zero byte is among its first 8,000 bytes, so the window never receives a file that would freeze it. A text and an image come with their `version`, the SHA-256 of their bytes. An SVG reads as text: the file view shows it through an `<img>`, so its scripts never run, and switches to its source. An image that does not decode shows the file view's message. `file.readOutsideFile` reads an absolute path the same way, with no working folder check.
- `file.listFiles` lists the working folder's files that git does not ignore (`git ls-files` with untracked files, tracked files deleted from the disk left out), at most `FILE_LIST_LIMIT`; outside a repository it walks the folder, skipping `.git`. An ignored folder is never walked. `file.gitStatus` reads `git status --porcelain` (with `--no-optional-locks`, so it never rewrites the index it watches) through the `Git` port, and a pure rule turns it into each changed file's status, relative to the working folder. Both tell a folder outside a repository (git says "not a git repository": no status, `walkFiles` for the list) from a git failure, a time limit included, which they raise as `GitFailed` with git's output, so a failure never looks like "no changes" or "no files".
- The file list is shared like the changes: `ChangeFeed.listFiles` keeps one `git ls-files` per working folder, run again only after a batch in which a path was created or deleted (a path on the disk differing from the last listing), an ignore file changed, or git's `index` or `HEAD` changed, so a change to a file's content runs none, and every reader of the batch, in any session, reads the same listing. With no reader on the folder, each call lists. A batch of more than 500 paths lists again without checking them. The UI keeps the listing it shows when a new one says the same, ignores a listing asked before the one shown, and ranks the files of Go to file from an index built once per listing; a longer query searches only the files the previous one matched, and a file that cannot enter the results shown is not scored.
- `file.watch` streams the paths changed on disk in the working folder, in batches of 100 ms, leaving out what git ignores and the `.git` folder (changes under a folder known to be ignored are dropped before they are queued, each name is queued once while it waits, and outside a repository nothing is ignored and no `git check-ignore` runs); a change to git's `index` or `HEAD` alone sends an empty batch, so the status is read again after a commit. One recursive `fs.watch` per folder (an FSEvents stream on macOS) is shared by every reader through `SharedFolderWatch`, opened with the first and closed with the last; the git dir of a linked worktree, outside the working folder, is watched the same way. Above it, `ChangeFeed` keeps one filtered feed per real path of a working folder, shared by every `file.watch` reader of every session in it, so `git check-ignore` runs once per batch. Each batch it sends increases a counter before any reader gets it; while the feed has a reader, `file.listChanges` and `file.readDiff` share one listing per batch, so a reader never gets a listing older than the batch it reads after.
- `file.listChanges` lists the working folder's uncommitted changes against HEAD (the empty tree before the first commit), untracked files included, through the `Git` port: `git diff --name-status` and `--numstat` with rename detection, limited to the working folder (`--relative`), and `git ls-files --others`, which a pure rule merges into each file's status, old path when renamed, and line counts. The listing carries the commit it compared with, so a diff of one of its changes runs `git diff` alone. A rename shows only once staged; unstaged, git sees a deleted and an untracked file. Outside a repository it answers `not_repository`; when git fails, `GitFailed` carries git's output. `file.readDiff` finds the path among those changes and runs `git diff` on it (`--no-index` against `/dev/null` for an untracked file), with `--no-optional-locks` so it never rewrites the index the watcher follows; a pure rule parses the unified diff in the server, off the window's thread, into hunks of numbered lines, pairing each run of deleted lines with the added run after it to mark the part that changed. A diff past 4 MiB (`DIFF_SIZE_LIMIT`) answers `too_large`, a binary one `binary`, a path with no change left `unchanged`. `file.listCommittedChanges` and `file.readCommittedDiff` do the same between `git merge-base HEAD origin/<default branch>` and HEAD, from the local `origin` refs with no fetch, so only what the branch's commits changed shows and what the default branch gained since, squash merges included, stays out; with no `origin` remote they answer `no_origin`, with no `refs/remotes/origin/HEAD` `no_default_branch`, and when the branch shares no commit with it `no_merge_base`. A listing depends only on HEAD and `origin/HEAD`, so each call runs one `git rev-parse` of both (commits, and `origin/HEAD`'s name) and lists again only when one of them moved, a fetch included; the last listing of the 32 folders read most recently is kept. `file.discardChanges` takes the paths the user confirmed and discards those still among the uncommitted changes, so a file the agent writes while the dialog is open stays: it runs `git restore --staged --worktree` from HEAD (the empty tree before the first commit) on the tracked ones, both paths of a rename, which deletes a file added since, and `git clean --force` on the untracked ones; a path with no change left is skipped. Every git command that takes paths runs with `--literal-pathspecs`, so a name such as `[id].ts` never matches `i.ts`. The flags that keep a repository's own config from running a command are in [Worktree](worktree.md). A branch with no commit yet has no committed changes. The UI lists and reads them again after each `file.watch` batch, with at most one read in progress and one waiting per reader, and shows a diff in the code view with each side's line numbers, read-only. The UI keys these reads by session and working folder, since `file.watch` keeps the folder it opened with, so when the session moves to another folder the git status, the changes and the folder's watch follow it.
- `file.writeFile` writes a file of a session's working folder with the same path check, through a symlink to its target. It refuses with `FileChangedOnDisk` when the file's bytes no longer have the `version` the client read (a deleted file included), and a null `version` writes over whatever is there. It writes a temporary file beside the target with the target's permissions, then renames it over the target, so no reader sees a file half written.
- The UI keeps what the user typed in a file in a kept-alive atom per session, working folder and path, with the version it was typed over, so it survives a session switch. An open file is read again after each `file.watch` batch that holds its path (never after one for another file): with no unsaved edits the new text replaces only the changed range, so the cursor and scroll stay. A file git ignores is not followed. Showing the file again reads it again; a new version under unsaved edits warns that the file changed on disk. Archiving, deleting or closing the project of a session with unsaved edits asks first, and drops them (`discardSessionEditsAtom`) only once the action succeeded, so a restored session does not bring them back.
