# File

What the design adds to the [glossary](../../GLOSSARY.md)'s terms in the `file` module, on the server and in the UI. The design shared by every module is in [the architecture](README.md).

- A link in an agent's answer that names a file opens it as a sub-view, the way the Files tree does: a relative path (from the working folder), an absolute path or a `file://` URL, with an optional line or range (`x.ts:42`, `x.ts:42:7`, `x.ts:42-50`, `x.ts#L42-L50`). The file view opens scrolled to those lines, selected; the request lives only in the UI, so the stored sub-view and a reopened file keep their own scroll. A path outside the working folder opens nothing and says why under the answer; a missing file gets the file view's own message.
- `file.readFile` reads a file of a session's working folder with the same path check as `file.listFolder`. Above 2 MiB (`FILE_SIZE_LIMIT`) it answers `too_large` without reading the file, and `binary` when a zero byte is among its first 8,000 bytes, so the window never receives a file that would freeze it. A text comes with its `version`, the SHA-256 of its bytes.
- `file.listFiles` lists the working folder's files that git does not ignore (`git ls-files` with untracked files, tracked files deleted from the disk left out), at most `FILE_LIST_LIMIT`; outside a repository it walks the folder, skipping `.git`. An ignored folder is never walked. `file.gitStatus` reads `git status --porcelain` (with `--no-optional-locks`, so it never rewrites the index it watches) through the `Git` port, and a pure rule turns it into each changed file's status, relative to the working folder.
- `file.watch` streams the paths changed on disk in the working folder, in batches of 100 ms, leaving out what git ignores and the `.git` folder; a change to git's `index` or `HEAD` alone sends an empty batch, so the status is read again after a commit. One recursive `fs.watch` per folder (an FSEvents stream on macOS) is shared by every reader through `SharedFolderWatch`, opened with the first and closed with the last; the git dir of a linked worktree, outside the working folder, is watched the same way.
- `file.listChanges` lists the working folder's uncommitted changes against HEAD (the empty tree before the first commit), untracked files included, through the `Git` port: `git diff --name-status` and `--numstat` with rename detection, limited to the working folder (`--relative`), and `git ls-files --others`, which a pure rule merges into each file's status, old path when renamed, and line counts. A rename shows only once staged; unstaged, git sees a deleted and an untracked file. Outside a repository it answers `not_repository`; when git fails, `GitFailed` carries git's output. `file.readDiff` finds the path among those changes and runs `git diff` on it (`--no-index` against `/dev/null` for an untracked file), with `--no-optional-locks` so it never rewrites the index the watcher follows; a pure rule parses the unified diff in the server, off the window's thread, into hunks of numbered lines, pairing each run of deleted lines with the added run after it to mark the part that changed. A diff past 4 MiB (`DIFF_SIZE_LIMIT`) answers `too_large`, a binary one `binary`, a path with no change left `unchanged`. `file.listCommittedChanges` and `file.readCommittedDiff` do the same between `git merge-base HEAD origin/<default branch>` and HEAD, from the local `origin` refs with no fetch, so only what the branch's commits changed shows and what the default branch gained since, squash merges included, stays out; with no `origin` remote they answer `no_origin`, with no `refs/remotes/origin/HEAD` `no_default_branch`, and when the branch shares no commit with it `no_merge_base`. `file.discardChanges` takes the paths the user confirmed and discards those still among the uncommitted changes, so a file the agent writes while the dialog is open stays: it runs `git restore --staged --worktree` from HEAD (the empty tree before the first commit) on the tracked ones, both paths of a rename, which deletes a file added since, and `git clean --force` on the untracked ones; a path with no change left is skipped. Every git command that takes paths runs with `--literal-pathspecs`, so a name such as `[id].ts` never matches `i.ts`. A branch with no commit yet has no committed changes. The UI lists and reads them again after each `file.watch` batch, and shows a diff in the code view with each side's line numbers, read-only.
- `file.writeFile` writes a file of a session's working folder with the same path check, through a symlink to its target. It refuses with `FileChangedOnDisk` when the file's bytes no longer have the `version` the client read (a deleted file included), and a null `version` writes over whatever is there. It writes a temporary file beside the target with the target's permissions, then renames it over the target, so no reader sees a file half written.
- The UI keeps what the user typed in a file in a kept-alive atom per session, working folder and path, with the version it was typed over, so it survives a session switch. Showing the file again reads it again; a new version under unsaved edits warns that the file changed on disk.
